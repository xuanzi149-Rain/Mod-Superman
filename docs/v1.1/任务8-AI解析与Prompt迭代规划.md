## 1. 目标与技能证据

产品目标：将用户自由描述转成保留原意、可被程序校验的制作建议，经必要澄清后形成与有效方案一致的文字说明。

技能目标：“掌握 Prompt 设计与迭代方法，能够通过任务拆解、示例设计、上下文组织及结构化输出约束优化模型表现。”这是一项待形成证据的目标，不能因保存本规划即宣称掌握或效果提升。

证据链：定义任务与预期行为 → 设计 Prompt、示例、上下文和输出协议 → 运行案例 → 分析失败 → 修改设计 → 比较并回归 → 记录决策和实际贡献。允许结果无改善或出现退化，不强制制造正向指标。

| 方法 | 项目应用 | 预期证据 |
|---|---|---|
| 任务拆解 | 分离需求解析与文案核对，中间由程序校验 | 输入输出、职责边界、失败路径 |
| 示例设计 | 用明确、模糊、多轮、未知能力和文案冲突案例约束行为 | 示例及选择理由、预期输出 |
| 上下文组织 | 区分原始目标、有效草稿、最新修正和未解决问题 | 上下文快照、多轮案例 |
| 结构化输出 | 模型提出受约束操作，程序校验并应用 | 操作协议、字段校验及拒绝记录 |
| 迭代验证 | 基线、错误归因、针对性修改、回归对比 | 版本差异、真实结果及接受/回退理由 |

## 2. 整体流程与依赖

模式与基础装备 + 最新消息 + 当前有效草稿 → 筛选相关上下文 → AI 解析/澄清 → 程序校验并计算 → 更新有效草稿或保留待解决问题 → 依据有效方案形成标准效果事实 → AI 核对自定义说明 → 交给任务 9/10 展示、确认和交付。

复用 B 的方案协议、稳定词条标识、能力与资源校验、修订号和摘要，不另建一套效果事实。解析与核对是两个主要模型任务，按状态调用，不要求每次澄清都调用文案审核。单次提交步骤有限，无无限自纠正循环，不引入 RAG、自主 Agent、多智能体或模型执行代码。

任务 8 负责模型处理、草稿更新规则及可交接的审核结果；任务 9 负责 HTTP、持久化、确认与后台交付；任务 10 负责页面展示与操作。三者先对齐协议和状态，任务 8 模块检查通过不代表网站已接通。D 的任务 11/12负责更系统的评测、修复与材料整理。

## 3. AI 任务一：需求解析与澄清

### 3.1 Prompt 设计

版本化 Prompt 必须明确：任务目标、可用依据、直接解析/追问/缺口处理规则、局部修改规则、输出结构。只依据提供的候选对象与能力，不编造标识、原值、效果或技术结论。用户输入和历史文本是待分析数据，不能覆盖程序边界。

模型提出建议；程序负责类型、范围、引用、资源、依赖和组合校验。未知能力必须保留用户原意并阻止生成。格式合法不等于语义正确，也不等于能力校验通过。

相对变化由程序依据明确基准计算；缺少原值、基准不明时追问。连续修改只涉及本轮明确要求，未涉及内容保持。通过稳定词条标识定位目标，区分撤销草稿操作、删除新增词条与移除原效果；目标不唯一时澄清。

非法建议不能覆盖此前有效草稿。本轮未落实要求必须单独保留并使方案不可确认；若实现选择保存合法部分，必须明确展示仍有阻断项，不能把部分保存称为整个需求完成。用户明确撤回或修正需求后才解除对应阻断。

### 3.2 示例库设计

以下为拟建案例类型，不是已执行结果；每例记录输入上下文、预期操作或问题、理由、关联规则。

| 类别 | 典型输入 | 预期行为 |
|---|---|---|
| 明确参数 | 重量改成 1 千克 | 直接提取，不无故追问 |
| 必要条件缺失 | 挨打后获得护甲加成 | 追问必要数值/持续时间，不自行补值 |
| 相对变化 | 在刚才基础上再减半 | 明确参照草稿和字段，交由程序计算 |
| 连续修正 | 持续时间改成两回合，其他不变 | 定位稳定词条，仅修改该项 |
| 混合需求 | 合法重量修改加未知机制 | 两项均有去向，保留缺口并阻止生成 |
| 文案/效果混淆 | 把临时效果描述改成永久生效 | 指出语义变化，进入澄清或效果修改流程 |
| 删除与撤销 | 删掉刚才新增的回血词条 | 区分新增与原有效果；后续对话不得复活被删词条 |

完整示例库用于开发，每次请求仅使用相关的少量示例，不把全库或全量游戏数据塞入上下文。Prompt 示例与独立验收案例分开维护。

### 3.3 上下文组织

按固定顺序构建：固定规则 → 当前制作模式/基础对象及必要原值 → 本轮相关候选能力 → 有效草稿与修订号/词条 ID → 原始目标及仍有效的澄清 → 未解决问题和最新消息 → 必要历史片段。

服务端有效草稿是当前状态依据，最新明确指令决定本轮修改，早期对话仅补充理解。候选信息不足时明确标记并补充查询或澄清，不能把“未放进上下文”直接认定为“程序不支持”。保留候选筛选依据和可复核的上下文快照，不记录密钥。

重点多轮案例：先要求“命中回血”，再改成“受伤回血”，最后要求“数值改成 3”。最后一步应修改受伤触发的原词条，不能恢复早期命中条件。

### 3.4 AI 操作协议

在 B 的完整方案之前增加受约束的建议层；具体字段名在开发时与现有协议对齐，本节不是已实现 API。

| 内容 | 目的与约束 |
|---|---|
| 本轮意图摘要 | 供人核对理解，不作为执行命令 |
| 基准修订号 | 绑定输入草稿；陈旧响应不能覆盖新草稿 |
| 修改操作 | 允许的增加/修改/删除/撤销类型、目标字段或词条、值或相对变化及基准 |
| 澄清问题 | 对应具体缺失条件，避免泛泛追问 |
| 未落实需求 | 原话、缺口、相关对象；不能静默丢弃 |
| 需求与操作对应关系 | 每项用户要求有操作、问题或缺口去向；映射本身仍需检查遗漏 |

程序先校验结构和操作，再校验目标、数值、资源与依赖，通过后才应用。未知键、错误类型、非法引用及陈旧版本应明确拒绝；失败保留有效草稿和原始输入，允许用户重试，不自动无限修复。

## 4. AI 任务二：文案与效果一致性核对

输入：程序从有效方案提取的标准效果事实、自定义名称/说明、词条映射及当前版本。背景故事与效果承诺区分处理。

输出：一致/存在冲突/信息不足，相关词条及文本片段，触发、对象、数值、持续时间、消耗的差异，以及不改变效果的建议措辞。

示例：实际为“受伤后护甲等级 +1，持续两回合”，说明为“永久提高护甲等级”，应指出持续时间冲突。审核器不能把参数改成永久；用户希望改变效果时，回到解析和程序校验。

只改措辞也需重新核对；参数或文案变化使旧确认失效。审核未完成、冲突未解决不能标为通过。可明确改用程序标准说明作为恢复路径，记录采用标准说明，不能伪装为 AI 审核通过；未解决的实际需求缺口不能靠替换文案解除。

5. 分类失败：解析错误、上下文错误、需求遗漏、追问错误、结构错误、文案漏检；程序缺陷或目录缺口单独归因。
6. 针对失败提出 V2 修改，保存假设、实际改动及理由；尽可能单项改变，多项同时调整时不把效果全部归因于某一项。
7. 在相同条件下复测失败案例和其他开发案例，再做独立验收。记录修复、新退化、未解决问题及接受/继续调整/回退决定。必要重复运行时如实保存所有结果，不挑选最好的一次。

至少完成一次有记录的基线—分析—修订—回归过程；若未观察到错误，可针对已声明风险提出修改假设并验证，不能编造 Bad Case 或强求采用新版本。

### 5.1 评估口径

| 维度 | 记录方法 |
|---|---|
| 结构合法性 | 可按协议解析的响应数/有模型响应的请求数；超时和调用失败另列，并保留总请求数 |
| 需求覆盖 | 有正确操作、澄清或明确缺口去向的需求数/标注需求总数 |
| 操作正确性 | 目标、动作、值及基准均符合预期的案例数/适用案例数 |
| 澄清表现 | 必要问题是否问到、明确请求是否被多余追问，分别计数 |
| 文案核对 | 冲突漏检与一致内容误报分别记录，注明适用样本数 |
| 多轮保持 | 未指定内容保持、删除不复活、最新修正被遵循的逐项结果 |

精确目标、操作与阻断行为按预期判定，措辞允许语义等价。不得用另一模型评分替代人工对关键案例的判断。当前不填通过率或提升值，不把小样本测量推广为一般能力结论。
