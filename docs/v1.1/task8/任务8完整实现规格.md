## 2. 总体流程与非目标

载入有效草稿与需求账本 → 构造上下文 → 解析 → 校验结构/引用/授权/版本 → 按依赖组试应用 → 保存独立合法组并保留阻断事项 → 从最终效果提取事实 → 核对/润色文字 → 绑定实际采用文本及方案摘要 → 用户预览确认 → 任务 9 调用 B 生成。

使用现有模型客户端、B 方案和固定生成器；不引入自主循环、执行代码、任意路径或新生成框架。最多一次初始解析、一次因内部信息缺失而补充目录后的解析、一次针对本版文字的核对；格式错误/超时不自动增加调用。用户新提交属于新请求。候选不足由程序补查，不能要求玩家提供 UUID。

D1—D5 保持：机制先行，机制确定后最多三个相关必需问题；独立合法组可保存；主动润色候选进入待确认预览、精确原文冲突须明确选择替换；完整状态加最近三个相关用户轮次；解析固定一个短例加最多两个边界例，审核固定冲突/一致对照。

## 3. 全能力操作映射

### 3.1 模式、资源与继承

| 用户意图 | AI 操作/处理 | B 落点与约束 |
|---|---|---|
| 修改已有/创建独立装备；选择基础装备 | change_context；模式/对象/携带策略不明确先澄清 | Plan.mode/base_equipment；已有模式须在修改目录，新建须模板体型资格通过 |
| 切换对象后清空或保留已有修改 | change_context.carry_policy=reset/revalidate，必须有明确原话 | 新上下文事务；reset 清空旧对象修改但保留明确未撤回需求为待重新处理；revalidate 逐项重验，失败内容不能静默丢失；不跨对象沿用确认 |
| 保留基础效果/重新设计 | set_inheritance_intent | 会话侧继承意图，B 无该字段；retain_base 沿用必要继承，reconfigure 逐项形成明确设置/移除清单，不能把所有值归零或直接删除所有底层效果 |
| 新装备外观复用 | select_reference appearance_equipment | Plan.appearance_equipment；仅新建；同类/槽位/武器与熟练组及特殊行为一致，体型资源完整 |
| 图标复用或恢复 | select_reference icon（null=恢复） | Plan.icon；必须有真实图标资源，不生成资产 |
| 固定获取入口 | select_reference acquisition | Plan.acquisition；仅新建；当前 B 核实入口 dammon_act1；不承诺库存刷新或无 Mod 冲突，不虚构容器入口 |
| 接受已审核特殊模板行为 | set_template_behavior | Plan.template_behavior；preserve_reviewed 要求用户明确接受当前 audit_id 指向的行为，不能从普通确认或旧对象继承同意；未知动作仍拒绝 |
| 撤销整次明确历史修改 | restore_snapshot | 同对象、同模式的服务端快照；恢复业务值和关联需求状态，作为新修订，不恢复旧确认；跨对象用 change_context |

change_context 与其他修改必须在一个独立上下文事务中处理；同一请求含切换与依赖新对象的要求时，先完成选择/继承及校验，再基于新上下文处理，不能把新要求应用到旧对象。change_context/restore_snapshot 不与其他 operations 混用；原话中其余意图记为阻断事项并带入下一次解析，不丢弃。

### 3.2 基础参数（全部 10 字段）

各项可 set_parameter；restore_parameter 将 B 覆盖值置 null，表示恢复继承，不猜一个原值写回。只有明确且可计算的数字量允许 relative_parameter。

| 字段 | 类型/允许值 | B 的实际生成与边界 |
|---|---|---|
| damage | NdS；N=1—10，S=4/6/8/10/12/20 | Weapon.Damage；不自动改双手伤害 |
| versatile_damage | 同上 | VersatileDamage；要求 Versatile 特性 |
| damage_type | Slashing/Piercing/Bludgeoning/Acid/Cold/Fire/Force/Lightning/Necrotic/Poison/Psychic/Radiant/Thunder | Damage Type；武器字段 |
| weight_kg | 0—100，最多三位小数 | Weight；当前协议只接受 kg；Prompt 将自然语言 g 表达转换为 kg 后提交，程序校验 kg 数值；不静默四舍五入 |
| rarity | Common/Uncommon/Rare/VeryRare/Legendary | Rarity；无隐含加成 |
| value | 整数 0—100000 | ValueOverride；配置价值不等于实际成交价 |
| enchantment | 整数 0—5 | DefaultBoosts 的 WeaponEnchantment；额外来源/未核对荣誉路径阻断 |
| weapon_properties | 唯一枚举数组 | Finesse/Light/Heavy/Reach/Twohanded/Versatile/Thrown/Melee/Ranged/Dippable/Magical；可整组设置或 edit_weapon_properties 集合增删；B 禁止改变需要资源重映射的结构特性，不把枚举合法等同组合合法 |
| armor_class | 整数 0—30 | ArmorClass；只对确有该字段的防具/盾牌 |
| dexterity_rule | none/full/capped_2 | Armor Class Ability/Ability Modifier Cap；盾牌不支持 |

relative_parameter 只开放 weight_kg/armor_class/enchantment/value；原值或当前有效值必须由程序提供。dice、稀有度、列表、类型“翻倍”等不可直接数字运算，应让用户明确最终值。整数结果不能截断、上限不能裁剪；用户目标仍保留为未满足。edit_weapon_properties 以当前有效集合为基准，add/remove 不得重叠；完整集合再经 B 校验。

### 3.3 六种效果类型（两种模式共用）

add_effect 使用请求内临时键；update_effect 指向既有稳定 ID、effect_kind 不得改变；remove_effect 只删除草稿新增效果。新增 ID、原生副本 ID 与文本句柄均由程序产生。改变效果类型须显式删除+新增，并保留用户意图关联。

| B kind | 可配置字段（结构详见 Schema） | 规则与生成去向 |
|---|---|---|
| constant | ability 六属性、amount 整数 -10—10 | PassiveData 的 Ability 加成；不假定全局属性上限行为 |
| bonus | bonus、amount 整数 -10—10、selector | initiative/movement/armor_class 的 selector=null；skill 使用 B 18 个技能枚举；saving_throw 选六属性；resistance 选伤害类型且 amount 固定 1，不能说“抗性 +3” |
| trigger | event、condition、target、action、dice/type 或 status_ref/status_draft_id、状态持续时间 | on_hit/on_heal/on_damaged；condition=always/target_full_health；target=self/target；原生 Passive 事件与 functor；遵守第 4 节组合规则 |
| independent_status | base_status、duration_turns 1—10、stacking、可选属性加成、bonuses ≤12 | 基础为 BOOST；只复用表现资源，原始回调不继承；replace/ignore/additive 映射 Overwrite/Ignore/Additive；独立 StackId |
| grant_spell | base_spell、healing/damage、range_m/area_radius_m、action_cost、cooldown、spell_slot/remove_spell_slot、status_duration_turns | 独立 Spell 副本与授予被动；金额字段 NdS，距离/范围 (0,100] 米，持续 1—10 回合；源技能 profile 决定可改项 |
| passive_copy | base_passive | 原生被动及执行依赖独立副本；必须同时显式移除基础装备上对应原被动。不是任意被动公式编辑器 |

技能动作 action/bonus_action/none；冷却 once_per_turn/short_rest/long_rest/none；法术位 level=1—6、amount=1—3。null 表示保留原设定；remove_spell_slot=true 才是取消法术位，必须与 spell_slot=null 配套。action_cost=none 只免动作类成本，不能声称所有资源免费；最终说明保留其他原生成本。

relative_effect 可用于 amount、range_m、area_radius_m、duration_turns、status_duration_turns；目标字段必须实际属于该类型并有明确有效基准。抗性的 amount 不可相对计算；属性金额整型约束保持；新增词条无原版对应值时 original 不可用。对嵌套状态 bonuses 先识别目标，输出完整新列表一次替换，由程序分配/保留子 ID，不允许任意 JSON 路径。

修改原版被动的数值效果，不能给 passive_copy 乱加 amount：若可用已支持类型明确重建，提出“移除原效果＋新建等价/修改效果”的同组方案并说明影响；否则记录具体规则缺口。不得缩减用户要求。

remove_original_passive 向 Plan.removed_original_passives 添加引用；restore_original_passive 从该列表移除。若同时存在替换用 passive_copy，恢复原被动必须先澄清如何处理副本，并同组变更，不能叠加两份效果。

### 3.4 名称、背景、效果说明

所有文字由 text_requests 表达，禁止绕过文案流程在 add/update_effect 内设置 display。

| 目标 | B 最终字段 | 规则 |
|---|---|---|
| 装备名称/背景 | Plan.display.name/description | 名称 1—60，描述 1—2000；精确原话保持；reset 为 null，但新装备名称不能为空 |
| 效果、状态、技能名称/说明 | effects[id].display.name/description | 名称与说明分开授权；用户自定义语义必须核对；默认标准说明也绑定最终事实 |
| 原生副本的关联/升环文字 | 由固定编译器生成依赖文本 | 不向模型开放任意依赖节点写入；父技能描述必须反映关联事实，关联文本按各节点最终成本/数值生成，避免覆盖为同一句话 |

mode=exact 要求 text 非空、style=null；rewrite 要求 style 非空，text 可为待润色原文；reset 要求 text/style=null。目标 owner 为 equipment、已有词条 ID 或同请求 add_effect 临时键。不存在的目标拒绝。未来程序分配 ID 后保留文本目标映射。

## 4. 输出协议与语义校验

parse-v1 与 review-v1 的所有对象禁止额外字段，数组上限见 Schema；禁止 NaN、无穷、重复 JSON 键和错误类型。文本按 B 检查空白/控制字符/长度；名称另用 60 字限制。请求编号、revision、context_digest 必须匹配输入，语法合法也不能重放。

### 4.1 parse-v1

顶层：schema_version/request_id/base_revision/context_digest/intent_summary/requirements/operations/issues/issue_updates/text_requests，全部必需。context_digest 由服务端对对象、有效草稿、需求状态、候选目录版本与相关上下文产生，模型只回传。

requirements 每项用原话 quote 和 meaning 记录需求，必须至少关联一个 operation/issue/text_request/issue_update，或 no_change=true 并解释无需变化；no_change 不可用于掩盖缺口。ID 在各自命名空间唯一，双向 requirement_ids 引用一致；所有原话引用须出自本轮或明确指向的既有问题。该映射有助检查遗漏，但本身不能证明语义无遗漏，仍需案例评测。

operations 共 15 种，字段均在 Schema 列明。group_id 是建议，服务端按写入冲突、引用依赖和同一文本目标重新合并组；同字段互相冲突的操作不按列表顺序猜最终值，返回澄清。恢复/切换操作不得与其他操作共存。

issues.kind：clarification 是用户需要作出的决定，必须有 question，可给已知候选 options；information_missing 是程序需要查询的信息，question=null；capability_gap 必须有输入中有效 evidence_refs，question=null。detail 保留具体缺口，不能只写“不支持”。本轮最多三个紧密相关 clarification；机制未定时只问机制，其余缺失事实记录为同一未解决需求，不能伪装成后台待查数据。

issue_updates 只允许引用已有问题 ID，带用户原话与替代操作/文字。answered 必须通过对应字段/选择验证才能解除；withdrawn 要求用户明确撤回；superseded 必须有关联新操作或问题可追踪。模型不能直接删除阻断。未在本轮输出的旧问题继续存在。

效果跨字段检查（结构 Schema 不替代本表）：

- trigger.action=status：status_ref 与 status_draft_id 恰好一个非空，dice/type 不存在或 null；duration_turns 必须 1—10。若引用独立状态，两者时长相同，修改时必须同组同步。
- trigger.action=damage/heal：dice 必填；damage 要求伤害类型，heal 禁止伤害类型；无状态引用和持续时间。即时值不被解释成持续治疗。
- on_hit 要求武器；on_heal/on_damaged 必须 self+always；自伤、治疗触发治疗、受伤触发伤害及递归状态拒绝。未验证其他条件不得映射成 always 偷换需求。
- independent_status 的 ability 与 amount 同时存在或同时不提供；至少有非零属性项或有效 bonuses，不接受空效果。所有新状态必须被合法触发引用，不允许孤立状态；嵌套 bonus 使用同样 selector 规则。
- grant_spell 同时设置 spell_slot 和 remove_spell_slot=true 拒绝；距离、范围、伤害、治疗和状态持续是否可改，以源 profile/依赖检查为准。
- passive_copy 必须引用实际 PassiveData、可解析闭包，原效果确在基础装备且移除路径已审核；普通/荣誉差异未知即阻断。
- update_effect 的 effect_kind 必须匹配既有类型；禁止修改 ID/kind；只合并明确 changes。changes 中 null 只可清除 B 可空字段；必需字段不得 null；不能取消状态时长。操作后验证完整对象。

### 4.2 review-v1

顶层：schema_version/request_id/base_revision/context_digest/plan_digest/items，全部必需。每个待审文本恰有一项，以 text_id/source_text_digest 绑定原文。模型不能遗漏、不增加无授权目标。

source_status=consistent/conflict/information_missing/not_provided；not_provided 仅适用于授权创作且无原文。conflict/information_missing 必须有 findings；consistent 无冲突 findings。findings.dimension 使用 Schema 的封闭枚举，quote 为实际原文片段；遗漏用 null；fact_refs 必须存在，事实不足可空但需说明缺少什么。

proposal_status=consistent/conflict/information_missing/not_requested；not_requested 必须 proposed_text=null 且 proposal_findings=[]；其他状态必须有 proposed_text。建议文本不能偷偷扩大授权范围。source 冲突不能因 proposal 正确而改成通过。

主动 rewrite 的 consistent 候选进入待确认预览；exact 原文冲突时保留原文与冲突，用户明确选择替换后再采用候选。采用标准说明记录 standard_used，不冒充 AI 通过。文本再次编辑/事实变化即失效。

## 5. B 衔接及必须实施的适配

以下为当前实现约束，逐项验收证据见独立验收覆盖矩阵。

### 5.1 请求事务与已有 Draft

1. 验证请求归属、去重编号、当前版本；生成中的草稿不得改。重复请求返回原结果，相对变化不重复计算。
2. 解析合法后，在服务端拷贝上规范化临时 ID、相对值、文本意图及问题。保留原始消息，不把模型摘要当作唯一用户目标。
3. 以依赖图合并操作组：状态与触发、原被动移除与副本、关联文本等同组。每组先在试算方案上校验；独立组通过才纳入最终候选；错误组保留原状和具体需求缺口。
4. 试算区分结构/能力错误与整体完成阻断（缺少新装备名称/获取、继承选择未定、待审核文字、未解决需求）。整体未完成不阻止合法局部保存，但绝不能因此绕过最终 B 门禁。错误码须显式分类，不能一律忽略 validate_plan 的返回。
5. 合并后的完整候选必须 Plan.model_validate；独立状态创建/删除等不能逐条调用 edit_effect 导致中间无引用或悬空；最终只调用一次 Draft.replace(...source='ai',expected_revision=...)，形成一个新修订。
6. 会话保存原话、问题账本、继承意图、文本审核状态和历史；每个未解决阻断映射为 Plan.unresolved 的可追溯短文本（最多 20 条）。超限则保留原草稿并要求缩小单次范围，不截断问题。最终反馈来自应用差异。

edit_effect 适合独立单项编辑，restore_parameter 的 null 语义可复用；复合事务不能假设现有 helper 已具备批量原子性。无参数变化但新增未解决需求/文案意图也应更新服务端修订，旧确认失效。

### 5.2 两处 B 字段规范化

- B 的 TriggerEffect 当前要求 duration_turns，即时伤害/治疗编译时却不读取它。AI 协议对此只允许缺省或 null，均表示没有持续时间；适配层仅为 B 合同填入固定技术占位 1，并记录 normalization=instant_duration_unused，不作为玩家效果、不向玩家追问、不允许模型自选。验收需确认生成 functor 未带持续语义；若未来 B 改为可空，应升级适配版本。
- B IndependentStatus 当前要求 ability/amount，即使用户只要护甲等 bonuses。AI 协议允许省略这一对；未来适配层以 Strength/0 作为零属性占位，并记录 normalization=neutral_ability_slot，再生成所需 bonuses；至少一个有效非零效果。此为与现有 Ability(...,0) 编译形式对齐的技术方案，需后续程序/产物验证，不能宣称游戏表现已实测。若验证发现非中性，必须调整 B 合同，而非给用户增加未请求属性。
- 状态 display 的结构必需由程序用标准名称构建，默认 description=null；嵌套 bonus ID 由程序分配。名称不从模型生成 UUID。用户明确自定义文字仍走审核。

### 5.3 自定义说明不是现成可用能力

当前 validate_plan 对 effects[*].display.description 非空返回 custom_effect_text_requires_phase_C_review；render_plan 仍以 summary 生成说明。不能通过清空用户文案或只删除此拒绝条件声称完成。

已新增服务端持有的审核凭据：绑定效果事实摘要（不含待审文案）、实际采用文字摘要、对象/效果 ID、目录/生成器版本与审核路径。该凭据不由模型提交，不是 Plan 内的布尔开关。

生成链所有入口（review、begin_generation、render_plan、generate_draft）均须校验同一凭据与最终方案，CLI 无凭据仍拒绝自定义说明。验收通过后编译器将已采用文本写入对应 Passive/Status/Spell 的本地化 Description；独立技能授予被动应同步描述，依赖/升环节点继续使用各自最终事实生成说明，不能复用根技能文本覆盖不同成本。

核对顺序：功能草稿 → 提取最终事实 → 文案审核/候选 → 用户采用规则 → 形成最终含文案 Plan → 生成/核验与事实、文本匹配的服务端凭据 → Draft.review → 预览 → 确认最终 revision+digest。凭据可绑定稳定事实/文本摘要以避免仅采用文本导致循环审核；任何语义事实或采用文字变化均失效，最终确认仍绑定最终 Plan。

Plan.display.description 当前可写背景，不意味着其功能承诺已核对；C 同样对名称/背景中的明确效果承诺执行一致性规则。标准说明恢复只解决文字问题，不解除原始机制缺口。

### 5.4 完整事实与确认

事实生成来自最终参数、继承内容、依赖闭包与编译规则。必须覆盖延迟治疗、升环成本、容器分支、状态触发/持续、剩余资源消耗、特殊行为和获取限制；不能只列模型直接改过的字段。

拟提供无文件写入的固定语义预览，与编译器共享规则；不为核对提前运行 PAK 生成。对当前无法可靠解释的原生表达式返回 information_missing 并阻止自定义文本被标为通过，标准原生说明的来源和限制明确标注。不能仅凭函数名推断游戏语义。

B 的 Draft.review(resources=...) 才使用实际资源校验分支；C 不得漏传 resources 然后把旧占位“不支持”当作真实目录结论。Draft.confirm 和 begin_generation 继续检查修订、摘要及资源变更；C 文案/问题门禁只能增加约束，不削弱 B 能力校验。任务 9/10 才负责 HTTP、持久化、页面与下载闭环。

## 6. 上下文合同与问题生命周期

parse input 必须含 request（request_id/base_revision/context_digest）、selection（mode/base_equipment/inheritance_strategy）、current_plan（有效 B 方案）、effective_values（相对运算基准及来源）、capabilities（version/category_summary/candidates/checks/completeness）、intent_state（goal/clarifications/open_issues/withdrawn）、latest_message（id/text/answers_issue_ids）、recent_history、snapshots（可撤销同上下文快照摘要，不发送文件路径）。缺少真实数据明确 null/unknown，不编造。

服务端始终保留完整当前草稿和未解决事项；模型的 requirements 是当轮解释，服务端账本持久保存跨轮未满足需求。新建继承未定会自动产生阻断。用户“从零新建”后需逐项核对参数和原有效果，特殊行为不能因选择重设而跳过。

内部查询补充一次后重解析，若缺口仍在则保留 information_missing，反馈“暂缺必要资料”而不是向用户反复问同一个问题。一次重解析的输出只能应用一次，以同一请求幂等处理。机制不明阶段不自动把合法参数建议和后续需要用户定值的需求合成完整效果。

review input 必须含 request、plan_digest、facts_digest、facts（id/owner/维度/最终语义/来源及缺失标记）、texts（id/owner/field/mode/source_text/source_text_digest/style/required_fact_ids）。审核不读取全聊天以免把旧愿望当事实。每段文本应覆盖哪些事实由程序设定；名称不要求写全效果，背景比喻不按字面误报。

上下文超预算不能静默截断当前方案、需求账本或已确认决定；先移除无关历史/候选/可选示例，再说明上下文不足并保留状态。调用日志记录实际模型版本、Prompt/协议/适配版本、输入摘要及错误，不记录密钥；案例需要复现时受原访问归属约束保存必要快照。
