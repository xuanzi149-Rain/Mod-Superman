## 2. 版本变化及机制

| 项目 | v1 | v2 |
|---|---|---|
| 内部资源缺失 | 笼统禁止索要 UUID | 明确不问任何内部标识；information_missing 的 question=null；补查后未找到时保留需求、建议描述效果，是否能创建独立词条仍待校验 |
| 上下文 | 无显式补查阶段 | capabilities.lookup_state 为 initial/expanded，便于区分首次缺失与补查后缺失 |
| 运行反馈 | 仅未解决事项 | 额外返回 recovery，明确未找到、可描述目标效果、需用户选择、未验证支持；最多一次补查，不自动替代 |
| 文案对象 | 未充分强调资源 ID 与文案 owner 的区别 | 整体文案用 equipment，词条用稳定 effect ID；唯一相关词条直接选择，歧义才问；程序拒绝未知 owner |
| 示例选择 | E09/E13 未被相关需求直接选中 | 在原有“固定 1 + 最多 2”预算内优先匹配只改文字和空目录技能请求；不新增示例总量 |
| 冲突建议 | exact 冲突“可以建议” | 事实充分时“应给出最小修正文案”；不替换原文，不改实际效果，仍由用户主动采用 |

保留 [解析 v1](../../../prompts/task8-parse-v1.md)、[审核 v1](../../../prompts/task8-review-v1.md) 和全部基线输出。当前运行版本为 [解析 v2](../../../prompts/task8-parse-v2.md)、[审核 v2](../../../prompts/task8-review-v2.md)，协议仍为 parse-v1/review-v1，没有修改 Schema 字段或原始 17 条参考答案。

原因判断边界：原 Prompt 已禁止索要 UUID，仍出现失败；因此不能只归因于“没写禁止规则”。补查阶段缺失和示例未选中是可观察的设计缺口，是否各自造成失败未做消融实验。此次指令、示例路由和程序校验共同变化，结果只支持整体修订判断。
