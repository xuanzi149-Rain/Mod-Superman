### 0.1 版本目标与问题定义

在 1.0 的装备基础参数修改流程上，扩展为“修改已有装备＋创建独立新装备”，支持独立词条、属性加成、装备授予的技能副本及自定义说明，并优化前端体验。

已知产品限制：1.0 网站开放基础伤害、双手伤害、中文名称、重量和稀有度，尚未开放复杂效果与新装备创建。用户是否主要受这些限制影响、影响多大，仍需调研，不能从“功能较少”直接推出“新增功能有需求”。

暂定问题定义：部分具备 Mod 安装经验的 BG3 玩家，希望调整已有装备效果或创建独立装备；基础参数修改可能无法满足目标，自行制作又可能受到游戏数据和工具门槛限制，因而寻找替代方案、降低要求或放弃。上述因果关系是待验证假设，不是已证实的调研结论。

### 0.2 目标用户与候选场景

核心目标用户：已经会安装和使用 BG3 Mod，有具体装备定制想法，但不熟悉 Toolkit、游戏数据结构和文件生成的玩家。当前交付继续以本地 Windows 使用为基础。

| 用户任务 | 触发场景 | 期望结果 |
|---|---|---|
| 已有装备调整 | 喜欢某件装备的外观或设定，但效果不适合当前玩法 | 保留其特色，调整指定属性、词条或技能 |
| 独立装备创建 | 希望定制装备，同时保留原版 | 获得名称、属性和效果独立的新装备 |
| 玩法或角色主题制作 | 希望装备围绕特定战斗风格发挥作用 | 组合常驻加成、条件效果和装备技能 |
| 制作中调整方案 | 初始想法不明确，或预览后改变主意 | 多轮修正，并准确核对最终效果 |

以上为候选场景，需用真实经历核对频率、影响和替代方案。专业 Mod 作者可补充技术反馈，暂不作为主要用户；不扩展为批量开发或任意脚本编辑工具。

统一使用“初步支持、需要收窄或修正、出现反证、证据不足”记录结论，并关联具体案例。当前 H1—H7 均待核验，不能因新表格已导入而改变状态。

| 编号 | 假设 | 支持证据应包含 | 反例或不足 | 验证方式 |
|---|---|---|---|---|
| H1 | 存在基础参数之外的装备定制需求 | 具体效果目标、触发场景及寻找或制作行动 | 基础字段或现成 Mod 已足够；只有未来意愿 | 真实经历与材料核对 |
| H2 | 制作知识是主要阻碍 | 明确卡在数据定位、规则理解或文件处理 | 主要困难是安装、时间、兴趣或兼容顾虑 | 操作经历，必要时观察 |
| H3 | 独立创建有单独价值 | 保留原版有明确用途，覆盖修改会产生实际问题 | 直接修改即可满足，新建仅为可选偏好 | 对照具体任务追问 |
| H4 | 复用已有资源仍能满足目标 | 接受已有外观、动画和机制后仍保留核心价值 | 核心诉求是新模型、动画或无法表达的机制 | 将真实构想与边界对照 |

### 0.4 用户调研设计与资料状态

调研以“最近一次具体经历”为主线：为什么想改 → 期望结果 → 尝试方法 → 阻碍 → 最终解决方式 → 是否仍有需求。先了解实际经历，最后介绍 1.1 方案，避免诱导认可。

建议先开展 3—5 人探索性访谈，覆盖需求未实现、尝试制作受阻及已找到解决办法的人。这是建议样本，不是已参与人数，也不能据此推断整体玩家比例。暂缓外部产品测试不等于取消调研资料分析。

| 维度 | 具体问题 | 判断重点 |
|---|---|---|
| 背景与环境 | 最近使用什么 Mod、如何安装？平台、模式和存档进度是什么？是否用过 Toolkit？ | 目标用户匹配度及安装约束 |
| 真实需求 | 最近哪件装备不符合想法？当时什么玩法？具体哪里不满意？ | 真实触发事件，不只收集愿望 |
| 期望结果 | 修改成功后，在实际使用或战斗中会发生什么？哪些必须改？ | 基础数值是否足够，效果是否必要 |
| 替代方案 | 找过哪些 Mod？最接近的方案哪里不合适？最后怎样处理？ | 现有方案是否已解决问题 |
| 制作阻碍 | 尝试到哪一步？最后无法继续时在做什么？能否展示记录或文件？ | 区分制作、打包、安装与验证困难 |
| 修改或新建 | 为什么要保留原版？同类装备一起变化会有什么影响？ | 新装备与影响范围控制的实际价值 |
| 资源复用 | 理想装备有哪些外观要求？仅用已有资源会失去什么？ | 复用边界是否保留核心价值 |
| 表达与核对 | 怎样描述期望效果？哪些参数已确定？如何判断工具理解正确？ | 澄清需求与核对能力 |
| 获取与安装 | 以前如何取得新装备？指定商人或容器是否适合当前存档？ | 交付链路的实际障碍 |
| 重要性与取舍 | 需求后来是否再次出现？没实现有什么影响？只能解决一项会选什么？ | 频率、影响及优先级依据 |

追问抽象回答：“制作很难”应追到实际停止的步骤；“想更强”应追到使用场景；“都想要”应追到最影响任务完成的一项。不用“是否需要 AI 创建装备”代替问题调查。

记录格式：用户与场景、具体目标、实际行动、阻碍与结果、证据来源、对应假设判断、暂定产品含义。分开保存用户原话、分析解释和产品需求；保留反例与未知，不将一条反馈直接解释为必须开发某功能。

### 0.5 需求分析、优先级与最小交付范围

| 期望结果 | 产品需求 | 拟采用方案 |
|---|---|---|
| 保留原版并制作自己的版本 | 新内容独立，不意外覆盖公共记录 | 新模板、Stats、文本及效果标识 |
| 准确实现复杂构想 | 能表达、澄清并检查组合效果 | 结构化词条、自然语言与手动编辑 |
| 文案与效果相符 | 关键条件和数值可以核对 | 说明生成、语义审核和最终确认 |
| 下载后取得装备 | 有明确获取入口及操作说明 | 固定商人或容器配置 |

此表是已确认方向对应的需求整理，不冒充访谈原话。技术开发按依赖排序：资料与目录 → 方案与规则 → 生成 → AI → 网站接入 → 评测。此顺序不等于需求价值排序。

产品优先级待资料分析后，按用户价值、证据可信度、频率与影响、实现及维护成本、依赖和风险决定；必须项说明缺少后会阻断什么任务。暂不编造评分或认定新装备、复杂词条、技能副本具有相同优先级。

用户最新确定：目标表中每类能力均须在 1.1 结束时支持修改和生成，游戏实测可暂缓。任务 2 的缺失规则必须继续补齐，不能作为缩减版本范围的理由；具体合法对象与组合仍须明确数据依据。调整投入顺序不等于删除目标能力。

### 0.6 已确认功能范围与排除项

| 类别 | 1.1 目标能力与边界 |
|---|---|
| 制作模式 | 修改已有装备；以已有基础创建独立新装备 |
| 展示文字 | 装备名称、背景描述、独立词条与技能名称、说明；延续简体中文，不承诺多语言 |
| 基础参数 | 稀有度、重量、配置价值；实际交易价格不等同配置价值 |
| 武器和防具 | 按类别开放伤害、伤害类型、双手伤害、附魔、武器特性、护甲及敏捷加值规则 |
| 效果 | 常驻属性与防护、条件触发、伤害治疗、状态及适用叠加规则；具体支持依程序能力确定 |
| 装备主动技能 | 从已有技能创建独立副本，修改支持的参数、消耗、冷却与说明；不覆盖原技能 |
| 美术资源 | 复用兼容的已有模型、图标、动画、特效与穿戴配置，不提供任意跨类型拼接 |
| 获取方式 | 固定商人或容器；具体位置、刷新及存档条件待核对 |
| 前端 | 红黑黄与三步流程保留，扩展复杂编辑、预览和恢复体验 |

用户自由定义目标，不受固定成品词条白名单限制；游戏允许某机制不代表当前程序已支持。缺少生成规则时停止生成并解释，不让 AI 临时编写执行代码。

不纳入本轮：新美术资产制作、独立于装备的职业技能系统、任意文件上传或代码执行、自动安装游戏、Script Extender/Lua、RAG、自主或多智能体架构、新前端框架。外部用户测试、逐项游戏实测与公开部署暂缓，保留反馈入口。

### 0.7 业务流程与核心规则

选择制作模式和基础装备 → 描述或手动编辑 → AI 解析 → 程序更新草稿及校验 → 澄清或说明能力不足 → 核对实际效果与文案 → 用户确认 → 生成、转换、打包与解包检查 → 下载 → 后续安装体验与反馈。

1. **共同事实**：AI 和手动编辑使用同一结构化方案，保存用户目标、草稿版本、修改来源、未解决问题及目录版本。相对计算由程序完成，原值未知时不猜测。
2. **已有装备**：保留未指定修改的内容；准确区分撤销草稿与移除原效果。需要修改共用词条时优先创建独立副本并替换该装备引用，不全局改写原被动；共用 Stats 影响范围仍明确提示。
3. **新装备**：生成独立模板、Stats 和文本标识，复用兼容资源，明确显示继承与改动；识别特殊标签、使用动作及相关依赖，不能盲目复制。
4. **词条与技能**：使用原生机制生成独立被动、状态或技能记录；按类型检查触发、目标、条件、资源和引用关系。不同机制不套用同一参数模型。
5. **文案**：背景故事可自由创作；效果说明依据实际方案生成。自定义改写由 AI 核对；只改措辞和改变效果分开处理，语义冲突先澄清。AI 审核提高一致性，不保证游戏效果。
6. **不支持处理**：指出具体缺失能力，保留输入和草稿，不静默丢弃部分需求。用户明确调整需求并重新预览确认后，才可继续生成；此规则优先于旧版部分保留说明。
7. **确认与恢复**：确认绑定修订号及内容摘要，参数或文案变化均使确认失效。模型或审核失败保留草稿，不无限自动重试；标准说明可作为明确的恢复路径，未审核内容不能标成审核通过。生成失败沿用重新预览确认后重试，禁止重复提交造成重复任务。
8. **交付与状态**：ZIP 含 PAK、修改清单和固定使用说明，新装备补充获取与依赖信息。解析、审核、校验、转换、打包失败分别记录；生成、打包、用户报告及游戏实测独立记录。

| 页面 | 1.1 拟增加内容 | 必须覆盖状态 |

## 1. 项目背景与目标

Mod-Superman 是辅助制作《博德之门 3》装备修改 Mod 的网站，同时作为 AI 产品实习求职作品。目标是让用户表达对一件指定装备的修改期望，核对明确参数后取得程序生成的修改包及固定说明。

项目价值假设是减少用户查找内部标识、编辑文件和处理打包步骤的负担。目前已实现对应流程，尚未测量节省时间、玩家任务完成率或普遍适用性，不将假设写为调研结论。

首版成功条件：测试玩家可以独立完成“选择—描述或手填—核对确认—下载—安装验证—反馈”。文件生成、打包、下载、用户报告和实际游戏观察分别记录，不能互相替代。

## 2. 用户与需求依据

目标用户是有 Windows 版游戏和基础 Mod 安装能力，希望调整指定装备参数的玩家。当前不要求用户掌握 Stats 标识、XML 或打包工具，但仍需自行安装启用并检查游戏效果。

依据包括用户已确认的项目范围与 MVP V1 三页前端、本地游戏数据目录、历史制作与游戏报告，以及当前接口和自动验收结果。此前玩家调查资料在 Notion，本次没有重新核查原始调查，不补写调查人数、比例或引语。

典型场景：选择第一滴血短剑，要求“基础伤害 2d6、重量减半”，检查原值和目标值，确认后下载含 PAK 的 ZIP，按说明安装并反馈。

## 4. 用户流程与页面结构

选择装备 → 描述修改期望或直接填参数 → AI 解析/澄清 → 后端校验 → 预览原值和目标值 → 用户确认参数并接受必要试验提示 → 排队/生成 → 下载 ZIP → 按说明安装验证 → 反馈。

| 页面 | 输入与展示 | 关键操作和状态 |
|---|---|---|
| 需求输入 | 当前装备、期望输入、近期交互、支持与获取说明 | 装备搜索、解析、补充澄清、手动参数；空输入/不支持/模型失败 |
| 确认并生成 | 全部修改的原值与目标值、解释、影响范围、试验提示 | 继续调整、一次“确认并生成”；等待及生成中 |
| 下载与验证 | 完整修改清单、PAK/清单/说明、制作编号 | ZIP 下载、安装说明、成功或问题反馈 |

修改对象、字段或目标值后必须重新预览和确认。确认页一次操作即可启动制作，不保留历史单独的“已确认，等待生成”页面。结果页不能把程序检查通过显示为游戏验证通过。

## 5. 核心功能与业务规则

### 5.1 搜索与消歧

搜索匹配装备名称或内部记录，前端仅查询已核实获取方式的对象。结果优先展示玩家能理解的效果和获取位置，不依赖 UUID 尾号让玩家猜测身份。普通首饰明确标注无固有魔法效果；获取条件有限制时标注。

无结果时说明其他候选仍待核实，给出已开放名称示例。底层共用记录不会自动证明两个模板属于同一可获取装备，也不据此自动合并。

### 5.2 输入、解析与澄清

自然语言输入最长 4,000 字符；空白输入被拒绝，支持 Ctrl/Cmd+Enter。上下文包括当前对象允许字段、原值、有效草稿及必要历史。

AI 负责理解、澄清和解释，输出结构化建议；程序二次校验。明确值直接提取；“减半”等由程序用 Decimal 计算；模糊要求先追问，超范围要求说明不支持。不能让用户文字、模型输出或原始代码绕过目录规则。

当前使用阿里云百炼 Token Plan 北京端点与 qwen3.7-plus；显式关闭思考模式。密钥仅在本地忽略的配置或服务端环境变量中保存，不发送前端，不写入文档。保留 DeepSeek 兼容代码不代表当前仍由其提供服务。

### 5.3 编辑与确认

“继续调整”弹窗允许编辑多个字段、增加对象支持且尚未加入的字段、移除字段，至少保留一项修改。保存时整体校验；取消不提交，未保存编辑可在同一草稿版本恢复。

可用文字继续调整已有草稿，其他参数按后端合并规则保留。存在不支持要求时，手动继续需明确接受仅保留支持参数。预览固定对象、参数及目录/生成版本；旧草稿版本或失效预览被拒绝。

历史少量参考方案之外的参数与组合按试验方案提示，需额外接受；试验确认不能替代合法性校验。本次生成包始终需要独立游戏验证。

### 5.4 生成与交付

后端读取已确认方案，生成最小 Stats 覆盖及必要本地化文件；不让 AI 自由编写最终 Mod。检查修改范围与结构后，使用 LSLib 创建 PAK，再解包逐文件比较并核对 ZIP。

ZIP 包含 `.pak`、`修改清单.json`、`使用说明.txt`。用户不必再次本地打包，但需解压、安装启用并验证。名称仅覆盖简体中文；共用 Stats 及继承记录可能共同受影响，不承诺只修改背包中的一个实例。

后台单次执行一个打包任务，最多两个等待；同一方案重复提交复用已有状态。生成失败或服务重启中断后，应创建新预览并重新确认，不自动再次生成。

### 5.5 说明与反馈

安装关键步骤来自固定模板，自动填入本次对象、参数、PAK 名称、版本依据及制作编号，网页说明读取同一 ZIP 文本，不由 AI 自由编写。

说明覆盖 Windows 安装启用、旧同对象包冲突、逐字段效果检查、停用恢复、共用记录范围和已知限制。目录版本上下文为历史记录 v4.1.1.7631656（来自用户截图），不代表本次新包在该版本已测。

反馈选择成功或问题，关联制作编号；问题阶段包含生成、打包、下载、安装和游戏效果，问题描述必填，游戏版本可选。反馈记为用户报告，不自动把游戏验证字段改成通过。

## 6. 异常、恢复与状态

| 情况 | 当前处理 |
|---|---|
| 空输入 | 就地提示；柔和闪烁两次，减少动态效果时静态显示 |
| 未知对象/字段、非法类型/范围、重复 JSON 键 | 后端拒绝，不能进入生成 |
| 模型超时或无效结果 | 保留输入、记录失败；可重试或直接填参数，不自动重试 |
| 草稿版本冲突/目录变化 | 要求刷新会话或重新选装备并确认 |
| 重复请求 | 请求编号去重，防止相对变化重复应用 |
| 页面刷新/网络中断 | 用保存的编号查询服务端；不把未知结果视为成功 |
| 生成失败/重启中断 | 明确失败阶段；新预览、新确认后重试 |
| 下载失败 | 重试已有文件，不重复调用模型或打包 |
| 下载过期 | 生成后 7 天失效，提示保存本地 ZIP |

方案状态包含预览、排队、生成中、成功、失败和中断。源文件、PAK、解包检查、下载和游戏验证分别记录。模型收到 HTTP 200 不等于解析完成。

## 7. 数据、访问与维护

本地运行时，服务数据保存在本机 `build/backend/mvp-local`；未来部署时放在服务器持久化目录。浏览器仅保存恢复所需编号、输入、编辑草稿及界面偏好，不能代替服务端记录。

| 数据 | 存储与作用 |
|---|---|
| 会话、草稿、方案 | SQLite records 表，payload 为 JSON；正常读取依据 |
| 访问归属 | owners 表，保存浏览器 token 摘要 |
| 阶段与错误事件 | events 表，记录阶段、结果及诊断，可关联会话/方案 |
| 用户反馈 | feedback 表，通过 plan_id 关联制作 |
| JSON 快照 | 兼容与诊断；数据库无记录时导入 |
| 交付 ZIP、PAK、检查结果 | 本地数据目录中的产物文件 |

匿名浏览器 Cookie 限制记录访问；清除 Cookie、过期或更换浏览器不能只凭编号取回记录。跨来源 POST 被拒绝；请求体上限 24KB。按 IP 每分钟最多 10 次模型请求和 60 次写请求，模型最多并发两次。

模型连接等待 10 秒、读取等待 60 秒，调用方总等待 65 秒；超时不自动重试，底层未结束请求仍占并发容量。诊断不保存密钥、请求头或完整模型原始正文；正常会话历史仍保存用户需求与结构化结果，不宣称完全不存内容。

服务启动及每日维护进行 SQLite 在线备份，并清理过期交付产物，不删除制作与反馈记录。备份仍在同一磁盘，异机备份和长期数据保留策略尚未完成。
